# Installation payroll lock rollout

## Connected payroll pause during a coordinated release

Set `DEPLOYMENT_ENV=production` and `CONNECTED_PAYROLL_MODE=paused` on both apps **before** deploying this pair. Restart every web/worker process when changing the mode; it is a process environment setting. Production defaults to paused when the value is absent or unrecognized. Only the exact value `enabled` activates the connection. Development/test default to enabled when unset; an invalid explicit value pauses them too. Staging refuses boot without an explicit `enabled` or `paused` value. The lead must add `CONNECTED_PAYROLL_MODE=enabled` to the staging Render services before this release; this PR changes no hosted settings.

1. Record both approved commit SHAs, paired backups, operator and rollback/forward-recovery plan. Drain old connected workers and in-flight calls on both apps: old versions do not implement this setting. Verify both apps have the production/paused environment values.
2. Deploy and migrate AIRE first, keeping it paused. Verify every old AIRE worker is gone. Deploy and migrate Payroll, keeping it paused, and replace every old Payroll worker too.
3. Configure AIRE's `payroll:configure_lock_rollout` and Payroll's `aire_lock_rollout:configure` for every source with the same approved `STARTS_ON=2026-10-16`, identified actor and reason. Keep the inventory and history gates below; the pause switch does not waive them or rewrite old evidence.
4. Run `bundle exec rails connected_payroll:status` in **both web and worker environments**. Confirm `mode: paused` and `enabled: false`, approved builds, migrations, durable queue schema, worker heartbeats, recurring schedules and both lock-rollout receipts. Existing production/staging readiness JSON also exposes `connected_payroll`. Verify ordinary AIRE clock-in/out, edits and approvals and ordinary manual Payroll calculate/approve/commit/checks/reports using authorized fixtures.
5. Set `CONNECTED_PAYROLL_MODE=enabled` and restart all AIRE and Payroll processes in the controlled activation window. Enable both promptly: if only AIRE is enabled, Payroll returns retryable HTTP 503 until its restart completes. Verify both status outputs show enabled, then verify pending deliveries and exact payment receipts. Existing idempotency remains authoritative; do not delete pending work or fabricate receipts. Review any overdue scheduled cutoffs before activation: they become eligible immediately when enabled.

While paused, AIRE still records outbox evidence but does not reserve or deliver it, consume delivery attempts, or mark it failed. Automatic cutoff finalization and Payroll-initiated manual locks are held, even for existing calendars without a rollout singleton. Employee/kiosk notices suppress automatic-lock countdowns. Payroll holds calendar delivery, event verification, receipts, manual-allocation sync and calendar source refresh; one-shot jobs recheck in one minute without incrementing exception retry budgets, while recurring dispatchers wait for their next scheduled run. Connected endpoints return 503 with `Retry-After: 60` before partial writes, and Payroll exposes capability flags that disable connected imports/locks with “Connected payroll is paused.” Ordinary manual payroll and ordinary AIRE time tracking remain available. Pending evidence and ordering/idempotency rules survive a restart and resume; pre-existing failures still require their normal recovery.

A scheduled calendar that AIRE never accepted before its cutoff remains subject to the existing late-publication rejection after resume. The switch does not backdate an unpublished schedule or waive history/cutoff guards. Retain that pending evidence and resolve it through the approved operator recovery path; ordinary eligible pending deliveries still drain automatically.

No schema migration, secret rotation, hosted setting write or deployment is included in these PRs. This switch controls new processes; it cannot cancel a request already in flight or stop an old binary. Re-pause and restart both fleets before investigating a release problem, and retain all financial/source evidence.


AIRE's payroll calendar belongs to the installation. Configure its cutoff activation once; it has no company foreign key.

After applying migrations `20261024080000` and `20261024090000`, and before enabling new calendar publication, run with the deployment's configured Rails environment:

```sh
bin/rails payroll:configure_lock_rollout STARTS_ON=2026-10-16 ACTOR='operator identity' REASON='Approved October manual and scheduled lock rollout'
```

The equivalent seed API is:

```ruby
PayrollLockRollout.configure!(
  starts_on: '2026-10-16',
  actor: 'Synthetic rollout acceptance',
  reason: 'Approved October rollout fixture'
)
```

The immutable singleton stores the boundary, operator identity, reason and timestamps. Configuration fails closed if **any** calendar before activation lacks explicit rollout evidence: manual `lock_mode` and a matching `cutoff_enforcement_starts_on`. This includes frozen legacy calendars. Stop deployment and obtain a reviewed resolution if the gate fails; do not rewrite history to pass it. No schedule, mode, publication revision or checksum is silently rewritten. Repeating configuration checks the same inventory before returning, so a legacy row that appears later also blocks an idempotent rerun. Standalone historical batches without a published calendar do not block configuration and remain unchanged. Creation also records `payroll_lock_rollout.configured` in the audit log, in the same transaction. The date must be the first or sixteenth of a month. Repeating the same date returns the existing configuration; changing it fails. Database triggers reject updates, deletion and truncation. This setting does not unlock frozen evidence.

New calendar publication fails closed without configuration with `PayrollLockRollout::NotConfiguredError`, mapped to retryable HTTP 503. Invalid publication fields still return HTTP 422. Send `lock_mode: 'manual' | 'scheduled'` and `cutoff_enforcement_starts_on: '2026-10-16'`; AIRE validates both against its own installation configuration. New preactivation manual publications must include **both** fields; omission fails even after nominal cutoff, preventing an old Payroll delivery worker from opening an unverifiable manual callback contract. Legacy scheduled callers on or after activation may still omit the fields; AIRE derives and freezes them from the installation boundary. October 1–15 is manual; October 16–31 and later are scheduled. Published mode and activation cannot drift, including through direct SQL updates. Request checksums retain existing replay compatibility; replays of retained publications do not rewrite their evidence. New values are also recorded in the publication revision and audit.

Manual calendars may first publish after their nominal cutoff. The nominal `cutoff_at`, date policy and existing cutoff trigger remain intact. The delegated cockpit Lock command requires the existing authenticated payroll-finalization capability, command ID, expected version and reason. It snapshots revision-ledger state at the database clock instant after obtaining the source ledger lock, including the frozen weekly overtime policy. Finalized rows, exclusions, settlement origin, audit and outbox are committed together. Repeating the command returns the same batch. The database also requires a persisted batch actor and an explicit manual-lock batch audit with the reason before a manual calendar can enter finalized state. This blocks an older scheduler from committing its nil-actor nominal-cutoff transaction during a mixed deployment. Scheduler calls and pending-cutoff claim fences skip manual calendars; a failed manual lock reports `attention_required` and requires another explicit Lock action.

Finalized manual period JSON includes `locked_at`, equal to the frozen batch cutoff with six fractional digits. Its nominal `cutoff_at` remains unchanged. Manual batch payload `cutoff_at` and `generated_at`, export cutoff and finalization metadata, discovery and outbox timestamps preserve that same microsecond instant. Historical frozen payloads are never rewritten. Settlement reconciliation uses the frozen batch cutoff so work included between nominal cutoff and Lock is not mislabeled as late. Later paid-time claims still subtract frozen evidence.

Manual published-calendar Lock freezes approved negative corrections, including a category reclassification's negative reversal leg, just as scheduled calendar finalization does. The frozen payload sets `requires_negative_adjustment_review: true` whenever it contains a negative adjustment. Lock freezes source evidence; it does not authorize compensation changes. It never fabricates a negative-adjustment acknowledgement or uses the Lock reason as negative approval. Cornerstone Payroll import still requires explicit negative-adjustment acknowledgement and an explanatory note through its existing workflow. Standalone manual batch finalization outside published calendars retains its own acknowledgement-and-note requirement. Missing-category guards are unchanged.

A late manual Lock remains allowed after the next scheduled period freezes. New overnight segments belong only to their calendar dates; existing later frozen claims remain in the settlement target, so omission from an earlier range does not invent a reversal. Changed or deleted represented work still produces correction deltas and negative-review requirements at its authorized destination. A rollout-aware manual calendar does not export dimensions after its end date, including negative/category/deletion legs, or create exclusions for later-only calculation context. This deliberately leaves later-period corrections with their named settlement case instead of silently absorbing routed work into an earlier Lock. The full employee/workweek context and prior balances remain in the allocator. If an earlier reduction changes frozen later OT, the successor exports the zero-total REG/OT reclassification exactly once; for example, +4 REG / −4 OT restores 44 total / 40 REG / 4 OT. The manual Lock does not reroute or close the later case, even when the same overnight source ID has legitimate earlier-date wages in its batch. A delayed scheduled worker orders regular batches by work period rather than snapshot timestamp: an earlier manual period locked later is permitted, while a genuinely later finalized work period still blocks it. It keeps the original scheduled revision cutoff and subtracts all existing claims; a newer earlier-period snapshot is not reinterpreted by the older scheduled snapshot. Scheduled calendars retain due fences and retry behavior. `next_scheduled_cutoff_at` is installation-wide on the calendar index and every calendar response. It selects the earliest unfinalized enforced scheduled calendar, including a delayed due calendar. It is null when none exists.

Migration preserves every existing calendar's stored scheduled mode and all frozen batches, revisions, checksums and outbox payloads. After configuration, unfinalized legacy calendars before activation are excluded from automatic due selection, direct scheduler finalization, pending claim fences and next-cutoff discovery. They are not silently converted to new manual publications. Review any such row before rollout; the immutable cutoff trigger still applies. Already-finalized historical calendars remain readable and retain their frozen settlement protections. Unlinked historical manual-processing workflows remain available outside published calendar ranges.

## Coordinated deployment gate and staging rehearsal

The approved path assumes no legacy preactivation publication needs reconciliation. The owner has confirmed read-only production inventories of zero Payroll publications/periods and zero AIRE calendars; recheck at the actual deployment window. This is deployment evidence, not permission to rewrite any history.

1. Quiesce **old Payroll publication and delivery workers** before the AIRE-first window. Stop new publications, retries, and operator calendar changes; record exact worker/build identities and verify no in-flight delivery remains. Drain **all old AIRE cutoff/outbox workers** and record that they have stopped. Keep both flows quiesced through migration, configuration and paired version verification. The manual actor database guard does not replace drainage.
2. In staging, rehearse against synthetic data first: zero inventories permit configuration; a preactivation calendar missing rollout fields must refuse initial configuration whether unfinalized or frozen; it must also refuse the same-date rerun if such a row appears afterward. Verify refusal leaves configuration, calendar, batch, rows, checksum, revisions and outbox unchanged. A standalone August 1–15 batch without a calendar must remain unchanged and permit configuration. Do not remove legacy evidence just to make the gate pass.
3. Apply the new migrations with workers drained. Inventory **all** preactivation AIRE calendars, including frozen rows, and all retained preactivation Payroll publications, including pending/delivered retries. Stop if any lacks explicit rollout fields. Run each app's configure task and verify the same October 16 boundary. Run the task again to exercise the idempotent inventory gate. Record operator, reason, builds, inventory and receipts.
4. Attempt a new omitted-field October 1–15 publication: AIRE must reject it without a calendar/revision/outbox. Publish with explicit fields and verify manual mode. Publish October 16–31 and verify November 7 at 17:00 Guam. Rehearse both orders: scheduled freeze then November 8 manual Lock; November 8 manual Lock then delayed scheduled freeze. Verify same-week and overnight segments once, frozen claims, original scheduled cutoff, correction review and callback/import agreement through the paired UI. Also freeze the scheduled period, edit its source, late-Lock the manual predecessor, verify exact receipts, then finalize/import its named successor. Confirm positive, negative and category corrections remain at that successor and zero-total OT reclassification is neither lost nor duplicated.
5. Verify both applications and new workers are on the approved paired commits before resuming publication, delivery, cutoff and outbox processing. Retain a release hold on any failed inventory or acceptance gate. No complex legacy reconciliation or historical rewrite is part of this rollout.

No production data changes or remote deployment are part of this implementation. Parent owns paired connected UI acceptance and release approval.
